Research · AgenticOS #2219

Choosing a task engine for AgenticOS.

Kacper Włodarczyk 19 October 2026 Issue #2219 Branch spike/task-queue-benchmark
Abstract

AgenticOS runs its background work on Prefect, which starts a new Python process for every run. On 18 October 2026 that design stalled production: about 1,650 late runs piled up on a VPS with heavy CPU steal, each paying a multi-second application import. We compared fourteen configurations of nine engines on three workloads drawn from the product: workflow chains, a mix of waiting model calls and CPU-bound ingestion, and a tenant flood with a worker crash in the middle. All ran under the same CPU and memory budget. Every task imports the real application. Every measurement comes from one event table on one clock. Process-per-run Prefect never finished the workflow scenario: 0.2 steps per second, against 500 to 1,300 for long-lived workers. Hatchet behaved correctly, but each workflow hop cost about ten times more, and it wrote 15 to 30 times the write-ahead log. With its fair scheduling on, the small tenant still waited longer than on the simple queues. A plain Postgres queue and Taskiq on Redis came through every scenario with no lost or duplicated work, at the lowest cost. We recommend one of the two, and record a duplication defect in our fair-queue prototype that must be fixed before it is used.

Section 1Why this study

AgenticOS runs three kinds of background work: periodic sweeps (expiring approvals, retrying sandbox teardown, delivering notifications), ingestion of uploaded documents into the knowledge base, and the agent runs that workflows (#1925) and triggers start without a person waiting. Today they go through Prefect 3's serve(), which starts a fresh Python process for every flow run.

A fresh process imports the whole application before it does any work. That takes 4.2 seconds on a laptop and 14 to 90 seconds on the production VPS, where CPU steal ran between 23% and 68%. On 18 October 2026 the runs fell behind faster than they finished. About 1,650 late runs starved the host, and the site went down until the backlog was deleted. The incident is written up separately. This study answers the question it left: what should run this work once workflows multiply it?

We did not want to decide from feature lists. Every candidate below runs the same tasks, importing the same application, under the same budget, and is measured from the same event log.

Section 2Candidates

Nine engines, fourteen configurations. They fall into three families, and the figures colour them that way throughout: queues on Postgres, which AgenticOS already runs; queues on Redis, which it also runs; and Prefect, the incumbent.

Section 3Method

3.1The tasks

Every engine runs the same five task kinds from bench/workload.py. A step is one workflow node: a database round trip and a sliver of CPU, after which it submits the next step of its chain through the engine's own client, the way the #1925 dispatcher advances a graph. An agent task stands in for a model call: it awaits for 2 to 10 seconds and then writes. A parse task is real ingestion: PyMuPDF extracts every page of a real PDF, about a second of CPU. A sweep is a scheduled one-query tick. A burst item is a short wait.

Every task process imports the real AgenticOS application first (bench/heavy.py). Process-per-run pays that import on every run, so a benchmark without it would hide the cost under study.

3.2Three scenarios

  1. Workflow. 50 chains of 10 sequential steps, all started at once: 500 steps. It measures the engine's overhead per hop, the gap between one step finishing and the next starting.
  2. Mix. Five minutes of Poisson arrivals: agent calls at 2 per second and PDF parses at 0.5 per second, with the engine's own one-minute scheduled sweep. It measures whether waiting work and CPU work starve each other, and how regular the scheduler stays.
  3. Tenants. One organization floods 1,000 jobs at once; a second sends one job a second for 90 seconds. Twenty seconds in, every worker is killed with SIGKILL and started again ten seconds later. It measures fairness, through the small organization's wait, and what a crash costs: lost, duplicated and re-executed jobs, and the longest stall.

3.3The budget

Workers get 3 CPUs and 4 GB, the share of the production VPS meant for background work. Services an engine brings with it, such as Prefect's server or Hatchet's engine, run in their own containers under their own limits, and their CPU and memory count against the engine. Postgres (2 CPUs, 1 GB) and Valkey (1 CPU, 512 MB) are shared by all. Each engine runs in its idiomatic production configuration, with 20 concurrent tasks per worker process where it has that setting.

3.4Measurement

Every task writes a started and a finished row, and the submitter an enqueued row, to one Postgres table, timestamped on one clock. Queue wait, run time, the hop between workflow steps, lost work (never finished) and duplicated work (finished twice) all come from those rows. A driver samples docker stats for every container once a second and reads Postgres's commit and WAL counters before and after each run. Every run starts from an empty compose project, and first measures cold start: the time from starting the workers to the first job finishing.

Section 4Per-hop overhead

The workflow scenario isolates what an engine adds between two steps of a chain. Engines with long-lived workers hand the next step over in 10 to 60 milliseconds. Hatchet takes 420. Prefect's background tasks take 2.6 seconds. Process-per-run Prefect takes 218 seconds, because each hop waits for a process slot and then an application import. In 20 minutes it finished 273 of the 500 steps.

Section 5Waiting and CPU work together

Agent runs mostly wait on a model; ingestion mostly burns CPU. An engine has to keep the first from starving the second. Almost every engine starts an agent call within a fraction of a second at the 95th percentile. Celery's prefork pool is the exception: each process sits blocked on a waiting call, so a new agent task waits 279 seconds at p95. Celery with a thread pool has no such problem.

The one-minute sweep separates the schedulers. Taskiq, SAQ, Hatchet and our Postgres queue fired on time. Procrastinate drifted by up to 29 seconds, and Celery Beat on the blocked prefork pool by 63. Dramatiq and Prefect's background tasks have no built-in scheduler, so in this configuration no sweep ran at all.

Section 6Fairness and a crash

In the tenant scenario a large organization floods the queue while a small one keeps sending a job a second, and every worker is killed at second 20. With a first-in, first-out queue, the small organization's jobs land behind the flood, so its wait climbs until the flood drains. Fair scheduling should flatten that climb. A good recovery should leave no gap in completions beyond the ten seconds the workers are down.

The small organization's p95 wait came out between 10 and 13 seconds for most engines. Hatchet's round-robin fairness improved on plain Hatchet, 18 seconds against 21, but stayed above the simple queues. Our fair Postgres queue came out near the bottom, at 10.1 seconds, level with SAQ. Only Prefect's background tasks were lower, at 8.6 seconds, in a run that did not finish in time. But the fair queue re-ran 141 jobs and finished 137 of them twice. That is a defect in the prototype's claim path after the crash, and it disqualifies the variant until it is fixed. SAQ lost no work, but after the crash 551 seconds passed between two completions, so its last job finished more than ten minutes in.

Section 7What each engine costs

On a host that already loses a third of its CPU to steal, an engine's own appetite matters. In the steady mix scenario most engines spent 20 to 30% of a CPU on the whole stack and wrote 1 to 3 MB of write-ahead log. Hatchet wrote 28 MB, about 15 times as much, because it keeps its own queue, state and history in Postgres. In the workflow scenario its stack, engine and database together averaged 278% CPU.

Section 8Cold start

Every run first measures how long a freshly started worker takes to finish its first job. The engines with long-lived workers come up in 4 to 10 seconds, most of it the application import. Hatchet takes 9 to 16 seconds, and Prefect serve() about 20, because its first run starts a second process and imports everything again.

Section 9Discussion and recommendation

  • Prefect is out in every form. Process-per-run cannot keep up with chained work, and its background-task mode is about a hundred times slower per hop than the alternatives, 2.6 seconds against 26 milliseconds, while still needing its server.
  • Celery's prefork pool does not suit waiting work. The thread pool fixes that, but Celery has no native asyncio, and AgenticOS is async throughout.
  • Hatchet is correct but expensive here. It brings a panel, retries, schedules and fairness, which are all things we would otherwise build. On this budget it costs ten times more per hop and 15 to 30 times more WAL, and even with fairness the small tenant waited longer than on the simple queues.
  • A Postgres queue and Taskiq give the best value. Both were clean in every scenario, among the fastest per hop, and among the cheapest to run. A Postgres queue adds no service, and it can claim work in the same transaction as the outbox from #1925, which removes a class of lost-message bugs. Taskiq adds nothing either, since Redis is already deployed, and comes with a scheduler.
  • Between those two, architecture decides, not speed. Taskiq, Dramatiq, SAQ, the Postgres queue and Procrastinate are within tens of percent of each other on every measure, and one run per cell does not rank them. What separates the two finalists is whether work is claimed in the outbox's transaction, or whether a ready scheduler matters more.

Recommendation. Move background work to long-lived async workers on either our own Postgres queue or Taskiq, and retire Prefect. Fairness per organization has to be written properly, with fencing, before it ships: the prototype duplicated work after a crash. These measurements contradict the earlier direction of Hatchet with Taskiq as plan B. That choice is the maintainers' to make with this data.

Section 10Threats to validity

  • One machine. Docker Desktop on Apple silicon, not the VPS. Absolute numbers will differ there. CPU steal slows every process start, which can only widen the gap for process-per-run.
  • One run per cell. Where engines differ by orders of magnitude one run ranks them. Where they are within a few tens of percent, as most long-lived engines are on hop latency and tenant wait, the order between them is not significant.
  • Idiomatic, not identical, concurrency. A process pool and an async loop have no common unit. Each engine ran its production-style configuration under the same CPU and memory limits.
  • CPU in the shortest runs. Resources are sampled once a second. Most workflow runs finished in about a second, too short for a reading, so the appendix shows no CPU for them. Costs are compared on the five-minute mix instead.
  • Unfinished runs. Procrastinate finished 1,089 of 1,090 tenant jobs before the 20-minute timeout, and Prefect's background tasks 1,088. Whether the remainder was lost or late is not established, so the tables report them as timed out rather than as losses.
  • Defects not yet diagnosed. The duplication in the fair Postgres queue and SAQ's 551-second stall are reported as observed. Their causes have not been traced.

Section 11Reproducing the results

The harness, the raw results and this page are on the branch spike/task-queue-benchmark under experiments/task-queues/. Each run leaves <variant>-<scenario>.json (settings, Postgres counters, resource samples) and .events.csv (every enqueued, started and finished event). The worker logs are packed in results/logs.tar.gz.

docker build -f backend/Dockerfile -t agenticos-backend:bench-base .   # from the repository root
cd experiments/task-queues
docker build -t tqbench:latest .
./run.sh hatchet workflow            # one variant, one scenario
./matrix.sh                          # everything, a few hours
python3 -m bench.report results > results/TABLES.md
python3 -m bench.site results report/template.html > report/index.html
