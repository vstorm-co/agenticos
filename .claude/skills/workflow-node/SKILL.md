# Workflow node development

Read `docs/reference/workflow-nodes.md`, `docs/workflows.md` and the matching backend
rules in `AGENTS.md`. Inspect `backend/app/workflows/contracts/definition.py` and a
nearby node with the same effect before choosing its contract.

## Avoid a parallel implementation

An existing node with different config may already express the request. Native
SaaS actions are generated by `nodes/integration_action/` from the integrations
catalog; use `native-integration` for a new product operation. A single authored
workflow belongs in its graph/spec, not a new Python node.

For a new node, follow `backend/app/workflows/nodes/<name>/`: registration in
`__init__.py`, execution in `_handler.py`, purpose and limits in `README.md`.
`tests/test_workflow_node_layout.py` checks that layout. Import the package from
`backend/app/workflows/_registry.py:load_builtins`; decorators alone do not load it.

## Define the execution contract first

A `NodeDefinition` has a stable id and a pinned version. Never replace a stored
`(id, version)` with incompatible ports, config or behavior. Retain old versions
or provide a deliberate migration and test old serialized graphs.

Use precise Pydantic config/input/output schemas and `Port` definitions. Decide
optional values, validation, output shape and stable failure codes before wiring
the handler. Return the workflow result variants; expected domain refusals become
explicit failures, while programming errors retain the normal error boundary.

Declare `effect_kind` and `retry_guarantee` honestly. A remote write that timed out
may already have happened; it is not safe to repeat without an idempotency or
reconciliation contract. Use the current workflow principal and resource checks,
not the publisher's credentials. Public workflows cannot borrow a person's account.
Workflow writes follow the authored graph; add an approval step where required,
rather than assuming the capability approval marker protects a workflow too.

Keep request/background transaction ownership and resource cleanup intact. Work
that outlives a request uses the job mechanism; read `background-task` when changing
execution or dispatch rather than starting an unowned asyncio task.

## Integrate the node into the existing editor

The backend node catalog is the source for palette/configuration schemas. Inspect
`frontend/src/lib/workflows/`, the workflow palette and field renderers before
adding a special case. Add a custom editor only when the schema cannot express the
interaction. Apply `frontend-feature` for permissions, translations and existing
UI components. Document actual input/output and error/retry behavior in the node
README and `docs/reference/workflow-nodes.md`, with translations when published.

## Verify what can fail

Start with `tests/test_workflow_registry.py`, `test_workflow_contracts.py`,
`test_workflow_node_layout.py` and the closest handler test. Cover registration,
schema/port compatibility, missing authority, cross-tenant resources, execution
context, refusal/error outputs and replay behavior. A transport mock alone cannot
prove durable execution, locking or duplicate-effect prevention. Add DB tests for
those changes and an editor test when UI behavior changes. Run small batches; CI
owns full coverage, migration and end-to-end gates.
