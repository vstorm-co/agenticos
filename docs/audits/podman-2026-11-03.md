# Podman deployment verification — 2026-11-03

Issue: [#2610](https://github.com/vstorm-co/agenticos/issues/2610).

Decision: support the manual path using Podman with **Docker Compose as its
provider**. Do not support `podman-compose` 1.6.0: the normal stack boots, but
its successful-migration dependency is not enforced. The Docker-only quickstart
points Podman users to the manual instructions.

## Migration failure reproduction

Save as `condition.yml`. No keys, application code or database are needed:

```yaml
services:
  migrate:
    image: docker.io/library/python:3.12-slim
    command: [python, -c, "import time; time.sleep(3); raise SystemExit(23)"]
    restart: "no"
  app:
    image: docker.io/library/python:3.12-slim
    command: [python, -c, "print('APP_STARTED_AFTER_FAILED_MIGRATION', flush=True)"]
    depends_on:
      migrate:
        condition: service_completed_successfully
```

Run once per provider, with separate project names:

```bash
PODMAN_COMPOSE_PROVIDER=/path/to/docker-compose podman compose \
  -p podman-condition-docker -f condition.yml up -d
PODMAN_COMPOSE_PROVIDER=/path/to/podman-compose podman compose \
  -p podman-condition-python -f condition.yml up -d
```

Docker Compose exits 1: `service "migrate" didn't complete successfully: exit 23`.
Its app remains `created` with no start timestamp. Podman-compose starts the app,
which prints `APP_STARTED_AFTER_FAILED_MIGRATION`. Thus a successful normal boot
does not qualify that provider for support.

## Sandbox results and adaptations

The unadapted rootless sandbox started and answered `/healthz`, but session
creation returned 502 with workspace permission denied. Its mapped uid was
correct; SELinux labels and socket access still prevented the operation.
The override and provisioning preserve global SELinux enforcement:

- Create the workspace on the **engine host**, inside the VM on macOS.
- Rootless: `podman unshare chown 10001:10001 <workspace>`. Rootful:
  `install -d -o 10001 -g 10001 <workspace>` as root.
- Mount the selected Podman socket at `/var/run/docker.sock` in `sandboxd`.
  Rootless socket ownership maps to group 0 in its user namespace: use
  `DOCKER_GID=0`, not the socket's host gid 1000.
- Disable SELinux labeling for `sandboxd` only, allowing engine socket access.
  Share the workspace label with `:z` for sibling sandbox mounts. Do not
  relabel the socket itself.
- Keep sandbox containers' labels and `no-new-privileges`. Runtime uid remains
  10001; neither sandboxd nor its sandboxes were changed to run as root.

The limit checks used a minimal Python runtime configured with 256 MiB RAM,
0.5 CPU and 64 PIDs. The shipped workbench was checked separately.

| Check | Rootless | Rootful |
|---|---|---|
| Open/close session through sandboxd HTTP | Passed | Passed |
| Execute as uid 10001 | Passed | Passed |
| Write/read workspace across commands | Passed | Passed |
| Preserve nonzero exit 7 | Passed | Passed |
| 0.3-second deadline terminates `sleep 30` | Passed | Passed |

A minimal runtime (`base_image=docker.io/library/python:3.12-slim`, no packages,
uid 10001) built through sandboxd's normal **Buildx** path on rootless Podman.
Session creation took 24.3 seconds once the BuildKit image was available. The
first cold attempt reached the HTTP client's 120-second deadline while Buildx
downloaded its builder image; this was not an API incompatibility. A separate
Docker SDK `images.build` request also succeeded against Podman's API.
No library change or release was needed.

The shipped workbench configuration resolved to
`pydantic-ai-backend-runtime:workbench-90eac1541cd9`. That exact image already
existed locally under Docker and was transferred to Podman rather than rebuilding
its package set. Through the committed override and app-to-sandboxd network, it
ran as uid 10001 and:

- wrote/read XLSX using pandas/openpyxl;
- generated a nonempty Matplotlib PNG;
- ran Node v24.19.0 and LibreOffice 25.2.3.2;
- executed the published agent's shell tool and returned its file marker.

Cold rebuilding every shipped package set, the desktop runtime, rootful
whole-stack startup and other Linux distributions were not exercised. Rootful
testing covered sandboxd and its sibling runtime containers.

## Detection regression

Podman's real `/version` response reports `Platform.Name` as
`linux/arm64/fedora-44`. `Components` includes `Podman Engine`, `Conmon`,
`OCI Runtime (crun)` and `Engine`. Quickstart therefore examines component
names, not the platform name. A real symlink named `docker` also changes
Podman’s `--version` output to `docker version 6.1.4`, and its native version
formatter has no Docker `Server.Components` shape. Quickstart identifies that
CLI through its native `system connection list` command, without needing a
running engine. CLI-shim and Podman-only cases remain covered;
installing Podman alongside working Docker does not block Docker.
