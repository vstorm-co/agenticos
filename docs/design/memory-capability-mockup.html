Memory
capability id: memory · category: knowledge
Enabled
Backend
Where memories live. Native is self-hostable & default; mem0 is opt-in.
Shape
Two independent switches. Both may be on; both off ⇒ the capability contributes nothing.
Files — named records + a derived MEMORY.md index. Exact recall.
Facts — short facts, recalled semantically (pgvector). Fuzzy recall.
⚠
Both shapes off — the capability won't attach. Enable Files and/or Facts.
Partition
Whose memories these are.
🏢
Shared — every end-user reads/writes one store (company memory). Promises no per-user isolation.
👤
Per-user — a private partition per end-user, keyed from a server-derived signal. On hosted pages, the embed widget and anonymous visitors there is no per-person signal, so per-user memory refuses there rather than pooling everyone into the owner's store.
Injection
How memory reaches the model.
⚠
Applies to operator-authored files only. Agent-authored memory is always tool-only — never injected, in any partition (the poisoning defense). Injection splices only trusted, operator-authored content into instructions, like context.
mem0 connection
Facts are stored in mem0. Files always stay native.
Vault kind api_key, purpose mem0. The model never sees it.
Cloud, or a self-hosted mem0.
🌐
Data residency. mem0 cloud sends memory content off this deployment. Self-host mem0 to keep it in-house.
ℹ
mem0 has no effect here. mem0 backs Facts, and Facts is off — so this config is treated as Native and no mem0 key is required. Enable Facts to use mem0. (Publish normalizes backend→native; it won't reject.)
