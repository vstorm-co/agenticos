The problem

Agents in five places.
Four questions nobody can answer.

One agent in a vendor's copilot, one in a notebook the data team wrote, one inside a SaaS product you already pay for. Then somebody asks:

What do we run?

No single list of agents, owners or versions.

What did it cost?

Every team with its own key and its own bill.

What did it touch?

Files, tools and systems, with no shared record.

Who said it could?

An approval in a chat thread, if anywhere.

The idea

The person who knows what the agent should say is not the person with commit access.

Most agent frameworks give you a library, so every change to an agent's behaviour is a pull request, a review and a release. AgenticOS gives that person a browser, a draft and a published version instead.

How it is built

Code defines, configuration composes

Code defines

Engineers, in typed Python

  • A capability is registered once: typed, tested, reviewed
  • Tools reach a model only through the capability registry
  • Sync connectors and MCP catalogue entries are added the same way

Configuration composes

Domain experts, in the browser

  • Instructions, model, tools and budget, set per agent
  • Every publish is a version; colleagues use the published one
  • Export the spec as YAML into your own repository
Configuration can only reach what code registered, so the builder cannot grant a tool that does not exist.
One agent

Where an agent is made

One page per agent, in the browser. Four areas:

  1. Name and status: what is published, and the Publish button
  2. Tabs: tools, limits, availability, versions
  3. Instructions: what the agent does, in plain language
  4. Model: which AI model answers
1Versions

What runs, and what you are editing

“Published, up to date with v6” is the version colleagues use. You edit a draft; nobody sees it until you press Publish. Export YAML keeps a copy in your own repository.

2Tools

Everything the agent may use

  • Toolbox: registered capabilities, e.g. search documents, run code
  • MCP servers: external tools such as Notion or GitHub
  • Limits: its own monthly budget
  • History: every published version
3Instructions

A brief, not code

What the agent is for, how it should work and what it must refuse, written like a brief for a new colleague. The person who knows the work can edit it.

4Model

Choose the model per agent

A provider and a model, with your own keys from the vault. Local models work the same way. Changing it is a setting, not a rebuild.

What it refuses

Much of the value is in what it refuses

refusedAnother organisation's key.A stored credential is sealed to the organisation that stored it, so a bug in an unrelated code path still cannot decrypt yours.
refusedA secret in an API response or an audit entry.Credentials are masked wherever they could be printed; a hint shows the last four characters, and logs redact tokens.
refusedThe model request that would breach the budget.Checked before the call, not tallied on the invoice. A run that fails still records what it spent.
Control

Three checks behind every run

  1. A budget, checked before every model request
  2. An approval: sensitive tools wait for a person
  3. A record of every run, and a hash-chained audit log
Captured from a test deployment
1Stopped by budget

A budget stops a run before it overspends

Monthly caps per agent and organisation, checked before each request to the model, not added up at the end of the month.

2Waiting for a person

The exact command, then a decision

You choose which tools must ask first. The agent pauses; the approver reads precisely what will run and presses Approve or Reject.

3On the record

What it did and what it cost

Every run keeps its agent version, tokens, cost, tool calls and what went into the prompt. Approvals, sharing and secret changes also join a hash-chained audit log per organisation.

Sovereignty

Your Postgres. Your Docker. Your network.

Self-hosted platform, hosted models

  • AgenticOS, documents, vectors and logs on your servers
  • Models from a provider, under your own contract and keys
  • Switch the model per agent

Fully local

  • The same platform on your hardware
  • Open models through Ollama or vLLM
  • Local parsers and tools keep data flows inside
Self-hosting the console does not make every model, parser or tool local: review each destination you configure.

Where it stops today

What it does not do yet

Source permissionsSharePoint ACLs are not mirrored per user. Scope the credential, share the collection.
Microsoft 365 triggersNo built-in Outlook trigger. Outlook connects through a third-party MCP service.
Visual workflow builderIn development. A plan, not a feature you can use today.
MFA, SAML, SCIMMulti-factor through your identity provider; SAML only via a bridge such as Keycloak; no SCIM.
Search quality toolsVector search with options; no reranker yet.
Scale-outSingle host with Docker Compose; no Kubernetes manifests.
Budgets under loadParallel runs can overshoot a cap slightly; a single queue makes it strict.
ResultsDepend on the model, tools and instructions, so evaluate them on your own task.
